日期：2026-08-21
狀態：**設計已確認（三個旋鈕由使用者裁決），實作中**
分支：`poc/hero-outro-pin`
取代：`architecture/2026-08-16-hero-scrub-dissolve-design.md` 的第一、三節（其餘仍有效）
相關檔案：`app/components/01.hero/HeroVideo.vue`、`Hero.vue`、`Hero.scss`、

## 〇、為什麼又改：前一版的兩個症狀

1. **「沒有 pin 的感覺」。** 逐點實測（1440×900）：退場期間舞台矩形恆為 `[0, 900]`、
   蓋滿視窗、`opacity: 1`；引言上緣從 1945 移到 775（確實 1:1 隨捲動移動），但直到
   最後 10px 之前完全被遮住。而 `applyDissolve` 對 `p` 的每一處使用都是門檻比較
   （0.005 / 0.02 / 1），**97.5% 的退場距離裡畫面不依賴 `p`** —— 捲與不捲畫面一樣。
   pin 是靠對比被感知的，而退場期間視窗整個落在 hero 佔位框內，除了影片沒有東西能動。

2. **「停在終點等影片播完」的等待感。** 揭露的雙條件（捲動走完 ＋ 影片播完）保證了
   設計師的「outro 走完才接 intro」，代價是捲得快的人要在終點靜候最多 2.5 秒。

使用者裁決：**放棄「強制看完 outro」**，改成「滑完 100vh 就收掉，引言原地淡入」。

⚠️ 這**直接推翻設計師的第三條需求**（「不要因為捲太快而看不到 outro」）。
100vh ＝ 900px，一般捲速 400–800 px/s 走完是 1.1–2.25 秒，而退場是 2.5 秒
⇒ 大部分人看到 45–90%，捲快的人更少。**這句話要原樣帶給設計師。**

## 一、機制：兩個階段，都由捲動驅動

| 階段 | 捲動範圍（1440×900） | 畫面 |
|---|---|---|
| **A 退場** | 0 → `vh(1)` ＝ 900 | 影片 sticky 黏在畫面上播退場段；引言在底下看不見地滑到 `vh(0.85)` |
| **A→B 交界** | 900 那一點 | 影片**硬切**消失（使用者裁決） |
| **B 淡入** | 900 → 900 + F（F ＝ `vh(0.3)` ＝ 270） | 引言停在 `vh(0.85)` 不動、`opacity` 0 → 1；orange core 同時從畫面正中央淡入 |
| 之後 | 900 + F 起 | 引言解除固定，正常往下閱讀 |

### 為什麼「引言不必真的靜止」

使用者要的是「不要看著引言一邊往上滑一邊淡入」。A 階段的滑動是 `opacity: 0`
**且**被一層滿版不透明影片蓋住 —— 完全看不見。只要把**淡入**推到它停好之後，
感知上就是原地淡入。故 A 階段的版面完全沿用現況，不必改成疊層。

### B 階段怎麼讓引言停住

`position: sticky; top: vh($intro-at)`，外面包一層高 `引言高 + F` 的容器 ——
**容器的高度就是停留距離**，停完自然釋放。

⚠️ **不可以用 ScrollTrigger 的 pin**：pin 的位置由主執行緒逐捲動事件寫入，而頁面
內容由合成器捲動 ⇒ 永遠慢一幀，慢的量等於當幀捲動距離。實測（每幀 10px）舞台 top
恆為 −10；真實滾輪一格 100–140px，於是圖層每幀上下彈跳 ＝ 2026-08-21 使用者回報的
「嚴重不自然抖動」。sticky 由瀏覽器同步合成，沒有這個問題。（同理見 `.sec1__hero`。）

## 二、幾何

```scss
$intro-at: 0.85;   // 退場結束時引言上緣落在螢幕的哪裡（設計核准過的那一格）
$exit:     1;      // A 階段吃掉的捲動距離（× 視窗高）＝ 使用者要的 100vh
$reveal:   0.3;    // B 階段吃掉的捲動距離（× 視窗高）
```

```
佔位高（.sec1__hero）= vh($exit + $intro-at) = vh(1.85) = 1665
  ⇒ 引言上緣螢幕位置 = 佔位高 − scrollY，在 scrollY = vh($exit) 時 = vh($intro-at) ✓
A 階段的 ScrollTrigger：start 0、end vh($exit)
B 階段的 ScrollTrigger：start vh($exit)、end vh($exit + $reveal)
```

⚠️ **ST 一律用數值 start／end，不要 `trigger` ＋ `'top top'`**：以 `.sec1__hero`
當 trigger 時 ScrollTrigger 量到的起點是 `vh($exit)` 而非 0 —— 它是 `position: sticky`
元素，量測拿到的是「黏住之後」的位置。2026-08-21 在基準線上實測到這個既有缺陷
（退場整段落在錯的捲動區間）。退場起點在語意上就是 page top，寫成數值最直接。

### 順帶解掉的一條約束

sticky 的黏著範圍被容器底緣限制，釋放點 ＝ 引言總高。前一版（`vh(1.2) + 200px`）在
1920×1080 上退場結束 1496、釋放 1480 ⇒ **餘裕 −16px**（影片在退場最後 16px 開始滑走）。
改成 `vh(1)` 之後退場結束 1296、引言總高 1460 ⇒ 餘裕 +164px，過關。
（375×667 一向寬裕：窄螢幕文字換行多、引言更高，而 `vh(1)` 更小。）

## 三、影片：不 seek、不變速、硬切

退場影片全程 **1× 播放**，不 seek、不變速、不暫停。兩條路已被實測否決，不要再試：

| 路 | 為什麼死 |
|---|---|
| 用捲動 seek 影片（逐幀 scrub） | 三支剪輯關鍵幀平均間距 4.2s，退場段（36–38.5s）內 pc/pad 各 1 個、**mob 一個都沒有** ⇒ 每次 seek 要重解 57–143 幀，實測單次 38–157ms ＝ 畫面只能更新 6–26 次／秒 |
| 用 `playbackRate` 追趕捲動 | ① 連續值在固定刷新率螢幕上必然 cadence judder：影片 30fps、螢幕 60Hz，只有 1× 與 2× 整除，中間值讓影格在 1／2 次刷新間不規則交替（rVFC 實測 `1 1 1 1 2 1 1 1 1 2 1 1 1 2 …`）。② 改離散 {1,2} 後**更糟**：每次**改變** `playbackRate` 都讓媒體管線重新同步（約 200ms 擾動），32 幀內切換 25 次、節奏出現 1/2/3 三種。加 600ms 最小駐留壓到 0–1 次仍有殘影 |

附帶結論（值得記住）：**每幀寫入相同的 `playbackRate` 是無害的**（實測 loop 與 outro
的呈現間隔完全相同、皆 33.3ms／0 掉幀），代價全在**改變**那一刻。

### 捲動連動的視覺：緩慢縮放

A 階段影片 `scale(1 → 1.06)`（`outroHoldScale`）。這是退場期間唯一跟捲動連動的東西，
沒有它「被釘住」就沒有對比可感知（見第〇節第 1 點）。

⚠️ **為什麼是縮放不是位移**：那一幀落後只對**位置**致命（落後的位移讀起來是反向運動），
對縮放無害 —— 實測暴衝捲動下最大逐幀跨步是 5.9px 高度變化（每邊約 3px、對稱擴張），
比 pin 版的 100–140px 反向位移小 40 倍。縮放也永不露出邊緣（放大只裁掉更多），
不必為了留餘裕先放大、改動核准過的裁切構圖。

## 四、orange core：進度 0 必須落在 A 階段結束

`OrangeCorePath` 的路徑起點寫的是 `sy = vhPx(0.5)`，語意就是「進度 0 ⇔ core 在畫面
正中央」。但它的 ST 起點在 scrollY 0，於是到了揭露的位置 core 早已前進一大段 ——
2026-08-21 實測（含 `0.9.0` 基準線）：core 螢幕中心在 scrollY 1080–2400 之間一直是
**1400 上下**，只有 scrollY 0 時是 450。這就是使用者回報「core 交棒銜接失效」的成因，
**且是既有缺陷，不是本次 PoC 造成的**。

修法（最小）：把 core 的 ST 起點與路徑起點**一起**平移到揭露位置。
```
core ST start = vh($exit)          // A 階段結束（＝ core 該現身的那一刻）
路徑起點 sy   = vh($exit) + vhPx(0.5)   // 於是進度 0 時螢幕位置 = sy − scrollY = 50vh ✓
```

**不在本次範圍內**：路徑中段因 `easeMove`（`MOVE_EASE`）而偏離 50vh 的行為是既有的、
刻意的（「雲霄飛車感」）。使用者要的是「從畫面中心**出現**」，不是「全程鎖在中心」，
故只修進度 0 的落點，不動運動曲線。

## 五、要重新驗證的下游（B 階段多出的 F 會把它們後移）

| 對象 | 為什麼會被影響 | 驗法 |
|---|---|---|
| `introFadeST` | trigger 是引言內容 group，B 階段的 sticky 改變它進入視窗的時機 | 淡出起點仍在「內容底緣升到視窗中央」那一刻 |
| `transitionST` | `start: 'bottom bottom'` 掛在引言外層，外層多了 F | core 抵達視窗中央時才 pin |
| `OrangeCorePath` 的 `endEl` | endEl 是引言，其幾何被 sticky 容器包了一層 | 終點仍落在「endEl 底緣貼齊視窗底」 |
| 後面三章落點 | 文件總高變化（佔位 2045 → 1665，另加 F 270 ⇒ 淨 −110） | 逐章量進場落點 |

## 六、驗收（沿用既有量測紀律）

| 要驗的事 | 正確量法 |
|---|---|
| 圖層有沒有抖 | **逐幀**讀 `getBoundingClientRect().top`，看是否恆為 0（不是看有沒有「感覺」）|
| 影格節奏 | `requestVideoFrameCallback` 的呈現間隔換算成刷新次數，看是否恆定 |
| 某一刻的畫面 | rAF 監看狀態翻面那一幀，**不是**截圖 |
| scrub 值 | 設好 scrollY 後等 400ms ＋ 兩個 rAF 再讀 |
| 視窗尺寸 | 量測前**必須**先設定視窗（`--chrome-inset` 會讓數字差 66px，2026-08-21 踩過）|

必測：

1. A 階段逐幀 `stageTop` 恆為 0（暴衝式增量 0/120/0/100/140… 模擬真實滾輪）
2. 影格節奏恆定、`playbackRate` 改變 0 次
3. scrollY = `vh($exit)` 那一刻：影片消失、引言上緣 = `vh($intro-at)`、core 螢幕中心 = 50vh
4. B 階段引言 `top` 不動、`opacity` 0 → 1 隨捲動
5. B 結束後引言釋放、正常上捲
6. 三個斷點的脫黏餘裕皆 > 0（375×667 / 1440×900 / 1920×1080）
7. 回歸：SKIP、`/#forum` 進站、`/#loop` 進站、回捲重播

## 七、已接受的代價

- **放棄「強制看完 outro」**（設計師第三條）。見第〇節的數字。
- **core 交棒退化成單純淡入**：影片被截在退場中途時，影片裡那顆 core 還在飛行途中，
  `HERO_OUTRO_CORE_ANCHOR` 對不上。這是設計文件第七節本來就接受的代價，只是現在
  對所有人生效，不只捲很快的人。
- **不動 `main` 的鎖**、不動 `INTRO_FADE_VH`／`TRANSITION_VH` 的值。
